# LIFE-ACCESS-STATE-001 · Stage B2A

## Результат

**Научный вердикт — `ACTION_DEPENDENT_DEPLOYED_SIGNAL` на development-панели.**
В замкнутом взаимодействии Z0-64 с прежним B3-обновлением повысил среднюю награду
с −20,02 у CARRY до −13,00. В отдельном факторном сравнении переход к
согласованному B3-обновлению увеличил награду Z0-64 до +20,90. Фиксированная
проверка собственного CARRY показала только +6,94 п.п. с нижней границей ДИ
0,00 п.п. Критерий улучшения основного считывания не выполнен.

**Инженерный вердикт — `B2A_VALID`.** Все 108/108 полных повторов и 9/9
восстановлений из pending checkpoint совпали с соответствующими оригинальными
траекториями. Проверены 2 592 записи действий. Целевые тесты B2A и регрессии B1
дали 17/17 PASS. Единственное предупреждение касалось устаревшего `pynvml`.

принимается на прежней development-панели. Исполняемый код B2A зафиксирован в

`exp/life-functional-sidecar-b2a`. SHA коммита поставки указан в `DELIVERY.json`.

Исследованы 12 прежних блоков из checkpoint 48 с одним правилом на жизнь. Каждой
политике на данном блоке назначена та же последовательность экзогенных сдвигов,
индексированных возрастом эпизода. Ошибка повторяет запрос и увеличивает штраф
с −0,25 до −1 за серию. Успех даёт +1 и предъявляет другой запрос. Сравнение
суммарной награды включает последствия выбранных действий и полученного при них
опыта. Параметры 48D-ядра, A, B/W и интегратор сохранены. Правила среды, выбор
панели и пороги описаны в `STAGE_B2A_ENVIRONMENT_RU.md` и `PLAN.json`. В рамках
B2A запускались только перечисленные development-режимы.

специфичность при `main`; перенос этого вывода на `aligned` отдельно не измерен.

## 2. Согласованное обновление и причинность

Для Z0-64 смена `main → aligned` дала +33,90 награды (95% ДИ [+23,48; +39,38]).
При одной и той же политике `aligned` Z0-64 превзошёл LIVE64 на +39,83
[+38,08; +41,98]. Обе читающие ветви имеют одинаковый бюджет в этом сравнении.
Разность эффектов `aligned − main` у Z0-64 и LIVE64 составила +32,75
[+22,81; +37,94] награды.
В Z0-64/aligned все 12 жизней имеют положительную награду (+18,75…+22,75).
Во время жизни режим в среднем увидел все 6 запросов при 3,58 у Z0-64/main.
Средний максимум серии ошибок уменьшился с 19,08 до 1,33. Для seed 821101,
mapping 0, `main` застрял на первом запросе (0 из 24, −22,50), а `aligned`
получил 22 правильных ответа (+21,50). Правило награды делает выход из ранней
петли ошибки особенно важным в этой среде.

При `aligned` источник прогноза и событийного признака совпадает с источником
выданного действия. Оба сигнала зафиксированы до раскрытия метки. Событийный
признак — разность `tanh(Z)` при запросе и при холостом ходе из того же снимка
с тем же RNG. В Z0-64 обе копии начинают из Z0. Main во всех режимах делает
собственный восьмитактовый прогноз и продолжает его физическую траекторию.
Согласование меняет совместно логиты и eligibility. Оно также меняет опыт,
поскольку новые действия меняют наблюдения. Этот дизайн показывает эффект
целой политики. Вклад логитов, направления и масштаба ΔK по отдельности не
идентифицирован.

В среднем `‖K_end − K_48‖_F` выросла у Z0-64 с 0,294 до 6,601 при переходе на
`aligned`. Сумма норм 24 фактических обновлений выросла с 0,477 до 13,317.
У LIVE64/aligned конечная разность составила 3,940, а сумма норм 4,870, при
точности 5,90%. Данные показывают крупное изменение режима записи; одного
увеличения нормы как причинного объяснения данный эксперимент не проверял.

## 3. Собственное считывание CARRY

На предъявленных средой запросах внутренний прогноз при Z0-64/aligned получил
35,42% против 17,36% при Z0-64/main. Наборы фактически запрошенных входов здесь
различаются. Фиксированная проверка использует все шесть исходных запросов по
одному разу, на копиях с замороженной K. Для live-Z теста до эпизода точность
составляла 38,89% в обоих режимах, после — 37,50% у `aligned` и 30,56% у
`main`. Парная разность +6,94 п.п. (95% ДИ [0,00; +16,67]) не проходит
порог 10 п.п. и нижнюю границу строго больше нуля. Средняя NLL живой пробы
выросла с 1,826 при `main` до 2,133 при `aligned`. В диагностической пробе из
Z0 точности 36,11% и 43,06%, парный ДИ разности [−1,39; +16,67] п.п. Успех
действий подтверждён для внешнего считывателя. Устойчивое улучшение доступа
из живого состояния CARRY остаётся открытым.

Средний максимальный `‖Z‖` на границах событий по режимам лежал в диапазоне
14,97–15,36. Это диагностика на данном горизонте. Для CARRY и строки таблицы
нейронная часть выполняла по 32 подшага за событие, для Sidecar/main — 160,
для Sidecar/aligned — 288. Соответственно 768, 3840 и 6912 подшагов за жизнь
без проб. Холодная и тёплая Sidecar имеют равный физический бюджет при одинаковой
политике записи. У среды задержка не участвует в награде. Среднее наблюдаемое
время на событие составило 108,3 мс у CARRY/main, 534,5 мс у Z0-64/main и
935,8 мс у Z0-64/aligned при двух воркерах. Во время режима TABLE также
исполняется диагностическая нейронная ветвь B3. Стоимость самой таблицы
включает только поиск и запись подтверждённой метки.

## Инженерная сверка

Независимый анализатор подтвердил, что запись действия сохраняется до реакции
и раскрытия метки, пересчитал переходы среды и все обновления K из логитов и
траекторий query/no-input. Проверены общий экзогенный поток по возрасту, старт
всех режимов из одного checkpoint, цепочка Z и RNG между событиями, источники
донорской K и неизменность B/W. В первом событии у каждого способа чтения
прогнозы и действия одинаковы до выбора политики записи. В режиме CARRY
обе политики совпали побитово во всех 12 парах.

Полный повтор сверил байты содержательных журналов и хеши снимков, включая
числовые массивы. Время исполнения исключено из требования идентичности.
Восстановление проверено на всех девяти режимах одного исторического блока
с позиции, на которой действие уже долговременно записано, а реакция и метка
ещё не раскрыты. Каждый из девяти повторов точно воспроизвёл оставшиеся 12
событий и конечный снимок. Сумма времени четырёх фаз — 22,95 мин с двумя
воркерами. После проверки исходного прогона тест согласованной записи сделан
самодостаточным для штатного pytest. Исполняемый экспериментальный код и
архив исходных тестов прогона сохранены.

## Границы научного вывода

- Один mapping на жизнь, похожие исторические начальные состояния и 24 новых
  события. Оценки относятся к development. ДИ основаны на 3 seed × 4 mapping,
  так что их ширина и чувствительность к отдельным блокам существенны.
- Среда связывает успех выхода из петли с доступом к новым запросам. Положительный
  результат измеряет политику в этом замкнутом процессе. Соответствие поведения
  при другом правиле переходов остаётся вне проверенного диапазона.
- K-only, same-age доноры проверяют чувствительность внешнего чтения в `main`.
  У соседних mappings могут совпадать отдельные метки. У `aligned` донорских
  траекторий нет, поэтому его более высокий результат относится ко всей
  согласованной политике.
- Разведены внешняя политика, полезность донорской памяти и способность CARRY
  прочитать её из живого Z. Из представленных данных вывод о переходе к двум
  правилам не следует. До такого перехода предусмотрен независимый аудит
  причинной схемы и интерпретации отрицательных контролей.

## Воспроизведение

Архив поставки содержит исходный Git bundle, снимок исполняемых исходников,
входные архивы QNUF и B1 с оригинальными манифестами, все журналы и snapshots.
`ANALYSIS.json` хранит точные оценки и результаты всех ворот. `per_event.csv` и
`per_life.csv` служат индексируемыми представлениями журналов. `lives/` содержит
оригиналы, `replay/lives/` — полные повторы, `resume/lives/` — возобновления из
pending checkpoints. Накладные расходы ввода-вывода входят в измерения времени.
Манифест `ARTIFACT_MANIFEST.sha256` покрывает файлы поставки. Отдельный SHA-256
идентифицирует ZIP.

После распаковки ZIP поставки и архивов `INPUT_QNUF.zip` и `INPUT_B1.zip`, из
клона `B2A_SOURCE.bundle` с веткой `exp/life-functional-sidecar-b2a` выполнить:

```powershell
$env:OMP_NUM_THREADS='1'
$env:MKL_NUM_THREADS='1'
$env:OPENBLAS_NUM_THREADS='1'
$env:NUMEXPR_NUM_THREADS='1'
python -m pqt_qcat.memory.functional_sidecar_b2a init --output $run --history $qnuf --b1 $b1
python -m pytest pqt_qcat/tests/test_sidecar_b2a.py -q
python -m pqt_qcat.memory.functional_sidecar_b2a factorial --output $run
python -m pqt_qcat.memory.functional_sidecar_b2a controls --output $run
python -m pqt_qcat.memory.functional_sidecar_b2a replay --output $run
python -m pqt_qcat.memory.functional_sidecar_b2a resume --output $run
python scripts/analyze_sidecar_b2a.py $run
python scripts/plot_sidecar_b2a.py $run
```

`$run` указывает на новую папку. `$qnuf` и `$b1` указывают на корни распакованных
исторических входов. Версии среды зарегистрированы в `SOURCE.json` и
`DELIVERY.json`. Идентификатор плана включает локальные пути к артефактам.
При смене путей хеш плана будет новым, а смысловое содержимое плана и результаты
внутреннего повтора проверяются теми же командами.

Для сверки уже сохранённой поставки без её перезаписи выполнить следующую
команду из клона ветки поставки. `$archivedRun` указывает на распакованный ZIP
с оригинальными журналами, `SOURCE.json` и `FROZEN_CODE.zip`.

```powershell
python scripts/analyze_sidecar_b2a.py $archivedRun --history $qnuf --b1 $b1 --verify-only
```
