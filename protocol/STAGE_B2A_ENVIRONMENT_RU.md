# LIFE-ACCESS-STATE-001 · Stage B2A

Историческая база — `aaf51b9b886e9223cbe07b5b0871e8c12ab42ba5`.
Принимается `B1_DEPLOYED_SIGNAL` на старой development-панели.
Stage B2A не меняет 48D-ядро, A, B/W, численный интегратор или коэффициенты
базового B3-обновления. Панель — три прежних seed, mappings с ID 0–3 у каждого,
всего 12 блоков. Префикс ID выбран до запуска для ограничения бюджета при
полном повторе каждой траектории. Старт — исходный checkpoint после 48 событий.
Длительность каждой новой жизни — 24 события.

## Среда

Состояние среды содержит текущий запрос, число последовательных ошибок и курсор.
Целевая функция в течение жизни фиксирована и совпадает с исторической
разметкой данного mapping. Первое наблюдение взято из прежнего события 49.
Для правильного действия награда +1, следующий запрос получается циклическим
сдвигом на величину от 1 до 5. Ошибка повторяет текущий запрос и получает
штраф −0,25 × (1 + min(число предшествующих подряд ошибок, 3)).
После правильного ответа счётчик сбрасывается. Правильное и неправильное действие
в одной позиции всегда приводят к разным следующим запросам.

Сдвиги для каждого seed×mapping получают из SHA-256 идентификатора блока
и номера события, фиксируют в `PLAN.json` и подают в сравниваемые режимы по
одному курсору. Семена новых инициализаций не вводятся. Среда выдаёт только
код запроса. Скрытая метка не передаётся ни в ядро, ни в правило выбора ответа.

Каждое событие проходит последовательность наблюдение → прогноз → durable
action → реакция среды → подтверждённая метка → обновление. Журнал фиксирует
пакет действия с flush/fsync и хешем его байтов. Среда реагирует только
на подтверждённый пакет текущего события. Награда и следующий запрос
появляются в журнале результата ниже по причинной цепочке. Неправильное
действие влияет на полученный опыт вследствие повтора, поэтому total return
оценивается по раскрытой траектории каждой политики. Это одна среда
с единым правилом, а не задача общего RL или смены контекстов.

## Выдача ответа и политика обновления

Сравниваются три способа прогнозировать внешнее действие и два варианта
присвоения ошибки. Во всех режимах работает одна основная непрерывная ветвь.

| Чтение | Фактически выданный ответ |
|---|---|
| CARRY | 8 тактов из живого Z основной ветви |
| LIVE64 | 64 такта на временной копии её стартового Z |
| Z0-64 | 64 такта на временной копии со стартом в архивном Z0 |

`main` использует исходный B3, то есть полный class-error по своему 8-тактовому
прогнозу и 8-тактовый событийный eligibility. `aligned` берёт логиты выданного
ответа и событийный признак той же ветви из пары query/no-input. Для Sidecar
обе траектории начинаются из одинакового состояния и используют тот же K/B/W/A
и парный RNG. В CARRY эти варианты совпадают по определениям. Только после
подтверждённой метки обучающий код подставляет оба значения в пакет обновления.
Физический Z Sidecar не записывается в main. До раскрытия метки проверяется
точное совпадение полного ожидающего feedback снимка с состоянием до вычисления
Sidecar. Policy aligned меняет одновременно масштаб времени и содержание
кредитного сигнала. Она не изолирует отдельно logits и eligibility.

K-only контроли используют Z0-64 с политикой main. Один подставляет
архивную начальную K, второй — K из траектории Z0-64/main другого mapping того же
seed на том же возрасте. Донор — следующий ID по циклу среди 0–3.
Нейронная main-ветвь в каждом контроле сохраняет собственные веса и обучается
после реального ответа. Для положительного контроля пустая таблица хранит
уже подтверждённую метку каждого запроса. До встречи с запросом она выдаёт
класс 1. За 24 события возможны не более шести ошибок. Main в этом режиме
также выполняет B3, чтобы можно было измерить его на этой последовательности.

Естественная стоимость на событие — 32 подшага у main вместе с его
теневой ветвью, дополнительно 128 у Sidecar и ещё 128 у соответствующей
контрфактической ветви aligned. Отсутствие padding делает стоимость разных
режимов различимой. Внутри главного контраста двух Sidecar budget совпадает.
Среда продвигается по индексам событий и не включает задержку вычисления
в переход или награду. Доступное сравнение относится к экзогенно общим сдвигам,
а не к фиксированному набору реально предъявленных запросов.

## Критерии и проверка

Положительный контроль требует ≥75% на каждой табличной жизни. Научный
сигнал внешнего результата требует, чтобы при политике main Z0-64 превосходил
CARRY, LIVE64 и оба K-only контроля не менее чем на 2 единицы суммарной
награды по среднему парному эффекту с нижней границей ДИ >0.
Отдельный критерий main-learning требует, чтобы согласованная запись
Z0-64 увеличила точность main на фиксированных шести query после жизни
на ≥10 п.п. относительно Z0-64/main с нижней границей >0. Те же запросы
отдельно проверяются из Z0. Online accuracy собственных прогнозов на
повторяемых средой входах не заменяет фиксированную проверку.
5 000 парных bootstrap-реплик отдельно пересэмплируют три seed и четыре
mapping. Интервалы исследовательские, поскольку development использован ранее.

Сохраняются итоговые checkpoints и снимок после выдачи действия в позиции
12 (нулевой индекс) до реакции и метки. Каждая жизнь повторяется заново
от исходного checkpoint. Отдельно для первого блока каждый режим
возобновляется из pending checkpoint. Сравнение выполняется только с
собственной траекторией: события, наблюдения, выданные действия, награды,
приращения и конечный снимок должны совпасть побитово.
